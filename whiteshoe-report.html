01

Legal documents are hostile to the people who need to understand them.

Terms of service written at a graduate reading level. Contracts with risk buried in boilerplate. Privacy policies designed to obscure, not inform. And on the other side: legal questions that require expensive professional time even when the answer is straightforward.

The legal industry has a scaling problem. The work is important, the stakes are high, and there are never enough qualified people to do it.

02

What if a law firm had no lawyers — only agents?

Not one agent. A team. Specialists that analyze, debate, challenge each other, transform documents, verify their own work, and learn from every engagement. A system where the agents genuinely collaborate: one proposes, another challenges, a third verifies, a human approves.

Whiteshoe is that system. Named after the act of turning rough stone into something polished and precise, it animates a team of AI legal specialists inside a workflow state machine with human gates, quality checks, and institutional memory.

Built on the Claude Agent SDK. Built by Legit (wearelegit.ai).

How It Works

A request comes in. The system reads it and asks one question:

What is the minimum viable workflow to handle this well?

counsel

3 steps · 1 agent

0 human gates
→

review

6 steps · 2–4 agents

1 human gate
→

roundtable

7 steps · 3–8 agents

2 human gates

The principle: don't use eight agents and three human gates to answer a question that needs one sentence. Default to the simplest path. Escalate complexity only when required.

The Evaluator Gate

Every workflow passes through an Evaluator Gate before delivery. This is Whiteshoe's core quality mechanism.

The problem it solves: correlated errors. If the same model writes an answer and checks its own answer, it makes the same mistakes both times. The writer can't see its own blind spots. You need a different model — a skeptic — to catch what the first one missed.

Writer

Specialist (Sonnet) — Produces the answer. Executes the work. Has domain knowledge but also has blind spots.

Checker

Evaluator (Opus) — Scores on 7 dimensions. Different model eliminates correlated confidence. Must be specific in critique.

Seven Evaluation Dimensions

DimensionWeightWhat it checks
Factual Correctness0.20Are the legal claims accurate?
Citation Validity0.15Do sources exist and support claims?
Policy Compliance0.15Does output follow firm standards?
Tool Consistency0.10Do tool calls match the reasoning?
Jurisdictional Accuracy0.15Right law for the right jurisdiction?
Internal Consistency0.15Does the output contradict itself?
Completeness0.10Are all parts of the request addressed?

The Evaluator doesn't grade on style — that's the plain-language specialist's job. It evaluates correctness. A wrong legal citation is a hard fail. A missing comma is not.

Document Ingestion

Legal work starts with documents. Whiteshoe has a full document ingestion pipeline that extracts text, detects structure, and makes documents available to agents.

Format Support

The parser accepts PDF (via pdf-parse), DOCX (via mammoth), and plain text formats. Each goes through format-specific extraction, then a shared structure detection pass.

Structure Detection

After text extraction, a structure detector identifies section headings, defined terms, and tables. This transforms a flat text blob into a navigable document tree that agents can reference by section.

10

Knowledge Base

Agents need reference materials — precedents, internal policies, regulatory guidance. The knowledge base provides searchable document collections that persist across sessions.

Indexing

Documents are chunked at section boundaries (target ~1500 words per chunk, max 2000). If no sections are detected, the fallback splits on paragraph boundaries. Each chunk is stored in SQLite with FTS5 full-text indexing.

Retrieval

Agents query the knowledge base via MCP tools during execution. The retriever performs ranked full-text search and returns the most relevant chunks with their source document and section heading. This gives agents citable references grounded in actual uploaded materials.

Built-in Knowledge

The system ships with curated knowledge files covering ethics audit frameworks, legal sanity checks, meaning preservation rules, pattern libraries, persona definitions, plain language guidelines, and scoring rubrics — seven knowledge domains that inform agent behavior.

11

Auth & Persistence

The system runs on SQLite (better-sqlite3) with WAL mode for concurrent reads. Live sessions stay in memory; SQLite stores the archive.

Dual Authentication

Two auth paths serve different clients. Browser users authenticate via email/password and receive an HttpOnly cookie (marble_token). API clients and agents use Bearer tokens (Authorization: Bearer shem_agent_...). Both paths resolve to a user identity that scopes all data access.

Data Model

Users

Email + bcrypt password hash. Auth tokens with expiry. User-scoped data isolation.

Matters

Client engagements with metadata. Status tracking (active, completed, archived).

Sessions

Workflow execution records. State snapshots, cost totals, timestamps. Linked to matters.

Knowledge Base

FTS5-indexed document chunks. Collection-scoped. Source tracking for citations.

All API routes (11 route files) are protected by the auth middleware. Public routes (login, register) are explicitly exempted. The middleware checks cookies first, then Bearer tokens, and attaches the resolved user identity to every request.

12

The Session

Every workflow — four steps or eleven — runs inside a session. The session is the system's memory for a single engagement.

Events

Real-time event bus with WebSocket streaming. Routing decisions, gate results, workflow transitions, cost updates, errors.

Audit

JSONL audit trail with SHA-256 checksum chain. Tamper-evident. Every tool call, gate decision, and cost event.

Cost

Per-session budget tracking with hooks. Blocks tool calls when budget is exceeded.

Memory

Institutional memory (lessons learned). Matter memory (per-client). Precedent library. Anti-pattern registry.

Gates

Human-in-the-loop decision points. CLI (readline) or API (async resolver). Approve, reject, or modify.

Debate

Shared debate board. Findings, challenges, responses, resolutions. RED/YELLOW/GREEN severity with confidence scores.

Workflow

State machine with preconditions. Phase-based tool permissions enforce what agents can do at each step — even if their prompt is ignored or manipulated.

The audit trail is particularly important. Each entry's hash includes the previous entry's hash. If a single line is modified, the chain breaks — tamper-evident by design.

13

Permissions

Agents can only use tools appropriate for the current workflow phase. This is enforced at the SDK level — not in the prompt, where it could be ignored.

canUseTool(toolName, input, options)
Not a Whiteshoe tool? → ALLOW
Orchestrator-only tool from subagent? → DENY
Tool allowed in this phase? → ALLOW / DENY

Each workflow template defines its own permission rules. During analysis, agents can post findings but cannot challenge each other. During synthesis, no one can run verification. The system enforces temporal boundaries on what's possible.

Workflow Templates

Every workflow is defined declaratively as a template — a data structure that says what the workflow is, not how to execute it. Templates live in a registry. The Router reads the registry. The executor reads the template.

interface WorkflowTemplate {
  id: string
  name: string
  description: string
  steps: string[]
  stepDefinitions: Record<string, GenericStepDef>
  availableTools: string[]
  requiredAgents: string[]
  orchestratorPrompt: string
  phasePermissions?: Record<string, DenyRule>
}

Adding a new workflow takes one file. Register it, and the Router sees it.

// src/workflows/templates/compliance-check.ts
workflowRegistry.register({
  id: 'compliance-check',
  name: 'Compliance Check',
  description: 'Regulatory compliance review.',
  steps: ['intake', 'framework_selection', 'analysis',
          'evaluator_gate', 'report', 'delivered'],
  requiredAgents: ['compliance-specialist', 'evaluator'],
  orchestratorPrompt: '...',
});

Design Decisions

Why different models for specialist and evaluator?

Correlated errors. If the same model writes an answer and checks it, it makes the same mistakes both times. The #1 failure mode in multi-agent systems is correlated confidence — two instances of the same model agreeing on something that's wrong.

Why phase-based tool permissions?

Prompt compliance is not guaranteed. An agent might ignore instructions about what tools to use. The permission system enforces tool access at the SDK level — the agent literally cannot call a blocked tool.

Why a state machine instead of free-form agent chatter?

Legal work requires auditability. You need to prove what happened, in what order, and who approved it. A state machine with preconditions gives you that. Step 5 cannot happen before step 4. Gate decisions are recorded. The audit trail is tamper-evident.

Why separate templates from executors?

Separation of what from how. A template says "this workflow has six steps." The executor says "here's how to run them." New workflows don't need new executors.

Why a revision loop instead of just failing?

Most quality failures are fixable. A specialist that forgets to cite a source can add the citation. Two revision loops catches most correctable errors. After that, send it to a human.

Why institutional memory?

The system gets better over time. When it learns that a particular type of clause is commonly missed in NDA reviews, that lesson goes into memory. The next NDA review starts with that knowledge. Every engagement teaches the system something.

Why SQLite instead of Postgres?

Zero infrastructure. The system deploys as a single process with an embedded database file. WAL mode gives concurrent reads. FTS5 gives full-text search for the knowledge base. No connection pools, no separate database server, no Docker compose. One binary, one data directory.

Why per-turn cost tracking?

The SDK only reports total cost at the end. But engagements can run for minutes. Users watching live agents want to see cost accumulate in real time, not discover a $12 bill after the fact. Per-turn estimation extracts token counts from each assistant message and multiplies by model-specific rates (Opus at $15/$75, Sonnet at $3/$15, Haiku at $0.80/$4 per million tokens).

Why 70 agents?

A real law firm has specialists. You would not send a tax lawyer to handle a patent dispute. The router selects the right team for each engagement — a simple NDA review might use 3 agents, while an adversarial M&A review could deploy 12. Each agent has a purpose-built system prompt tuned for its practice area. Users can also build custom agents via the Agent Builder. The cost is in prompt engineering, not compute — only the selected team runs.
